0. Стенд

Откуда сервис

Продолжение API из ДЗ 8+9+10 (hw8910-broken/service.py, backends.py): та же последовательность «загрузить артефакт → сверить SHA-256 → прогреть → стать готовым», ограничение одновременной обработки с очередью и отказом до постановки в очередь, версия в ответе берётся из памяти процесса, а не с диска. Добавлено: потоковая выдача (NDJSON), отдельные /livez /startupz /readyz, метрики Prometheus, обработка SIGTERM (снятие готовности и дренаж), идентификаторы в каждом ответе и журнале.

Что Как
Артефакт models/sim-A.json, models/sim-B.json (~0,5 КБ, «модель-имитатор»), хеши в models/SHA256SUMS; при сборке образа sha256sum -c
Источник версии для всех реплик неизменяемый образ llm-sim:0.1.0 (артефакты внутри); Helm values задают model.version и ожидаемый model.sha256
Проверка версии при старте backend.load() пересчитывает SHA-256 файла; несовпадение → load_failed, /startupz = 503, Pod не становится Ready
Связь ответа с версией заголовки X-Request-ID, X-Pod, X-Model-Version; финальная строка потока done содержит request_id, pod, model_version, model_sha256, backend_mode, session_id, cache, queue_s
Журнал JSON-строка на событие (accepted, finished, cold_request, rejected, sigterm, warm, load_failed) с request_id, session_id, pod, version
История диалога передаётся в запросе (messages), в Pod не хранится; префиксный кеш — только оптимизация
Для настоящих весов (не делалось) том ReadOnlyMany (NFS/объектное хранилище через CSI) или init-контейнер, скачивающий веса по закреплённой ревизии с проверкой хеша в emptyDir; для RWO-тома все реплики пришлось бы держать на одном узле

1. Опыт A. Прогрев, обновление и откат

Нагрузка во всех шагах A (experiments/exp_a.py, values-exp-a.yaml): прогрев backend 20 с; клиент loadgen-0 — короткие ответы (16–20 частей по 50 мс), пуассоновский поток 4 запроса/с; клиент loadgen-1 — длинные потоки по 500 частей (≈ 25 с), 0,05–0,1 запроса/с. Keep-alive у клиентов выключен, чтобы каждый запрос заново выбирал Pod через Service. Тайм-аут клиента 60 с. Линия Ready/EndpointSlice снимается раз в секунду (timeline.jsonl), журналы Pod — pods*.jsonl, сырые попытки — short.jsonl, long.jsonl.

График 1. Верх: число Pod в Ready (без завершающихся), ready-адреса в EndpointSlice обычного Service, Ready и фактически прогретые (по событию warm в журнале Pod), созданные, но не Ready Pod, Ready по версиям. 1.1 Прогрев: исходный дефект → исправление

Гипотеза. Если startup/readiness проверяют только то, что HTTP-процесс отвечает, новый Pod попадает в EndpointSlice за секунды после старта и получает рабочие запросы, пока backend ещё 20 с греется.

Воспроизведение (probes.mode=http, kubectl rollout restart на 15,6 с при нагрузке):

новый Pod 2: создан → Ready → прогрет 19,2 → 22,2 → 40,7 с 38,3 → 59,4 (warm) → 60,5 с

Строка «создан → Ready» и EndpointSlice — из timeline.jsonl, «прогрет» — событие warm из журнала Pod. 26 из 100 отказов пришлись на первые 8 с — ещё до rollout restart: Pod, созданные самим helm upgrade на probes.mode=http, тоже сразу стали Ready, и kubectl rollout status сообщил об успешном выпуске, пока оба backend были холодными. При дефекте rollout к тому же идёт быстрее, чем греется backend: оба старых Pod завершены к 22 с, а первый новый прогрет только к 37 с — 15 с без единого рабочего backend.

Причина. Готовность определялась состоянием HTTP-сервера, а не backend. Сервис сам защищён: непрогретый backend отвечает 503 backend_warming и пишет cold_request — без этого он бы молча обслуживал запросы непрогретым.

Изменение. startupProbe → /startupz (200 только после загрузки артефакта, проверки хеша и прогрева), порог 25 × 2 с = 50 с > прогрева 20 с с запасом; readinessProbe → /readyz (прогрет и не получал SIGTERM); liveness остаётся /livez с отдельной целью. Повтор того же опыта: 0 отказов, 0 cold_request, EndpointSlice получает адрес нового Pod только после warm. Красный/зелёный прогон той же проверки — results/tests/red-probes-http.log / green-probes-warm.log (раздел 5).

1.2 Rolling update A → B под нагрузкой с длинными потоками

Гипотеза. С maxUnavailable: 0, readiness по прогреву, preStop: sleep 5 и terminationGracePeriodSeconds: 60 (> длинного потока 25 с + preStop) обновление проходит без 5xx и без оборванных потоков.

Опыт (rollout-A-to-B): первый длинный поток отправлен на 8,4 с, helm upgrade на B — на 20,5 с, rollout status завершился на 65,5 с (45 с: два Pod по ~22 с прогрева, последовательно из-за maxSurge: 1).

Механизм дренажа виден в журнале (warmup-warm/pods-*.jsonl): при SIGTERM процесс пишет {"event":"sigterm","running":1,...}, снимает /readyz, перестаёт принимать новые соединения и дописывает активный поток; Pod исчезает только после этого. Временный рост задержки на 40–50 с — прогретая, но одна реплика B принимает долю трафика, пока последняя A завершается (p95 TTFC 0,43 с против 0,26 с без обновления).

1.3 Заведомо неготовая B и откат

helm upgrade с model.version=B и неверным model.sha256 (000…0) на 16,2 с. Новый Pod pvxjg: загрузка падает на проверке хеша, /startupz = 503, через 50 с startupProbe перезапускает контейнер (0/1 Running, 1 restart — bad-release/bad-pods.txt). В EndpointSlice он ready: false, serving: false (bad-endpointslices.yaml), поэтому из трафика исключён; оба Pod A продолжают обслуживать. helm history: ревизия 7 «Upgrade complete» — Helm без --wait считает выпуск успешным, хотя rollout застрял; признак сбоя — rollout status/неготовый Pod, а не статус Helm.

Откат: helm rollback llm 6 --wait на 76,4 с, 0,6 с (старый ReplicaSet A не уменьшался из‑за maxUnavailable: 0, удаляется только неготовый Pod B). За весь шаг: 606 из 606 ответов успешны, все 606 — версии A (model_version и model_sha256 в финальной строке каждого потока), 0 отказов. Отдельная проверка версии после отката — tests/test_k8s_version.py (раздел 5).

1.4 Принудительное завершение процесса

POST /admin/crash → os._exit(137) в Pod 7dv8w на 30,6 с от начала нагрузки (аналог OOM/segfault: без SIGTERM, без дренажа). Клиент повторяет до 2 раз с backoff 0,5 с × номер попытки; повторы записаны отдельными строками с attempt = 2, 3.

Показатель Значение
оборвано потоков на упавшем Pod (попытки) 3 (truncated: 1 длинный, 2 коротких)
попытки с отказом соединения в первые 1,3 с 6 (connect_error: kube-proxy ещё направлял на мёртвый адрес)
попытка, попавшая в уже перезапущенный, но холодный процесс 1 (503 backend_warming через 1,7 с)

запросы: запланировано / отправлено / попыток / повторов 618 / 618 / 696 / 78

Что оказалось важнее обрыва. Пока реплика перезапускалась, вся нагрузка (≈ 4,8 занятых слота коротких + ≈ 2,5 длинных потоков в среднем) пришлась на один Pod с 8 слотами: очередь заполнилась до 32, и 13–24 с после сбоя Pod отвечал 429 queue_full (89 попыток), а повторы клиента добавляли нагрузку. p95 TTFC коротких в этом прогоне — 10,6 с. Вывод: двух реплик недостаточно для N−1 при такой нагрузке; повторы нужно ограничивать бюджетом с jitter, а ёмкость считать с запасом на одну потерянную реплику. Холодный ответ через 1,7 с показывает, что для Pod, перезапущенного «на месте» (тот же IP), защита в коде (503 вместо обслуживания холодным backend) нужна и при правильных пробах: kube-proxy обновляет правила с задержкой.

Ограничения A. Один узел kind: нет сетевых задержек между узлами и переноса Pod. Наблюдатель опрашивает API раз в секунду, поэтому времена событий точны до ~1 с. Журналы Pod собираются kubectl logs во время шага; без внешнего сбора журналов они пропадают вместе с Pod (в первом прогоне так и случилось — повтор с LogCollector).

Прогон router-skewed-run1 пришлось повторить: во время первой попытки ноутбук уснул, и генератор зафиксировал это сам — максимальное отставание фактической отправки от запланированной 6597 с (в остальных прогонах ≤ 0,06 с). Испорченный прогон сохранён в results/exp-b-invalid/ и в сравнение не входит.

Горячая реплика ждёт, у другой — свободная ёмкость

Причина, исправление, повтор

Причина. ClientIP-привязка закрепляет всех пользователей клиента (или NAT/шлюза) за одной репликой. Ключ слишком крупный: 80 % трафика попадают в одну очередь, ёмкость второй реплики не используется. Обычный Service решает это лишь отчасти: балансирует соединения, а не запросы, и случайно разносит диалоги по Pod (cache hit падает до 0,75).

Исправление — готовая политика consistent hashing with bounded loads (HAProxy hash-balance-factor 125). Ключ — сессия (X-Session-ID), а не IP. Диалог идёт на «свою» реплику, пока у неё не больше 125 % средней загрузки (HAProxy считает активные запросы на сервер), иначе — на следующую по кольцу. Тот же сценарий с тем же списком запросов (3 × 2 прогона):

  • задержка: p95 TTFC 2,40 с против 4,29 (без привязки) и 7,42 (ClientIP) при uniform; 1,89 против 2,66 и 4,45 при skewed; разброс между прогонами минимальный;
  • отказы: 0 во всех шести прогонах (ClientIP — до 17 %);
  • распределение: 57–61 % на загруженный Pod при любом профиле;
  • локальность кеша: доля hit 0,82–0,83 — почти как у ClientIP (0,89) и выше, чем без привязки (0,75). Проигрыш в попаданиях (~7 п. п.) дешевле очереди: промах стоит 0,4–1,2 с, а очередь на горячей реплике — секунды.

Что требует отдельной проверки на настоящем inference engine. (1) Загрузка как число активных запросов — грубая мера: для LLM важнее занятые KV-блоки, длина очереди prefill и размер батча, поэтому нужна cache-aware маршрутизация с этими сигналами (SGLang router, llm-d / Gateway API Inference Extension). (2) Реальная стоимость промаха — prefill в токенах на данной GPU и влияние на TPOT соседних потоков, у нас она линейна по символам. (3) Вытеснение KV-кеша по памяти, а не по числу записей. (4) Длина префикса (одна сессия на ключ — грубо; общий системный промпт между сессиями наш хеш не учитывает). (5) Маршрутизатор — отдельная точка отказа и лишний хоп (~1 мс у нас); нужны ≥ 2 реплики HAProxy.

Ограничения B. Нагрузка задана близко к насыщению (без привязки p95 уже 3–5 с), поэтому различия крупные; при низкой загрузке политики почти не различаются. Один узел. Ходы одного диалога могут уйти до завершения предыдущего хода — тогда даже на «своей» реплике будет промах.

Горячая реплика при HPA

Повтор горячей реплики (exp-c/hot): skewed 4 rps через ClientIP-Service, keep-alive включён, 300 с. HPA масштабировал 2 → 3 на 28 с (новый Pod Ready на 42 с), но третий Pod не получил ни одного запроса: клиенты 0, 1, 3 остались на glftp (1091 запрос), клиент 2 — на tl7q6 (77). Через 6 мин HPA вернул 2 реплики.

Когда средний CPU вызовет масштабирование. HPA считает desired = ceil(n × avg_util / target), где avg_util — среднее по Pod от request. Горячий Pod упирается в limit 1 ядро = 200 % от request 500m; холодный ~20 %. Среднее (200 + 20)/2 = 110 % > 60 % → масштабирование. Если бы target был выше (limit/request)/n = 100 %, либо limit равнялся request, перегрузка одного Pod из двух не подняла бы среднее выше цели: горячая реплика страдала бы, а HPA бездействовал. Почему новая реплика почти не получает запросов: ClientIP-привязка в iptables хранится по IP клиента и пересматривается только по истечении таймаута (10800 с) или при исчезновении endpoint; keep-alive удерживает и сами соединения. Новых клиентов нет, поэтому весь прирост ёмкости пропадает. HPA добавляет Pod, но не перераспределяет трафик — это задача маршрутизации (bounded load из раздела 2).

4. Что и как измерялось

Клиент (app/loadgen.py) — open-loop: запрос уходит по расписанию, не дожидаясь предыдущих. Длительности меряются time.perf_counter() (монотонные часы), абсолютные отметки time.time() — только для сопоставления с Prometheus и журналами Pod. По каждой попытке сохраняются scheduled_wall и sent_wall (отставание генератора send_lag_s; в нормальных прогонах ≤ 0,06 с), время заголовков, TTFC (до первой строки type=chunk), inter-chunk latency (N − 1 интервал для N частей; среднее и p95), полное время, статус, Pod, версия, request_id, число частей, cache, серверное время в очереди. Ответ — части имитатора, токены модели не считаются, поэтому TTFT/TPOT здесь не применяются.

Учёт (analysis/metrics.py): запрос (req_id) и попытка (attempt) различаются, повтор — отдельная строка. Считаются запланированные, отправленные, успешные (ok), отклонённые (rejected, 429), http_5xx, оборванные (truncated: 200, но нет финальной строки done), просроченные (timeout), connect_error. Перцентили p50/p95 — nearest-rank только по успешным, рядом всегда n_ok и доля ошибок/тайм-аутов. Сырые данные: results/requests.csv (все попытки всех опытов, 15,2 тыс. строк) и results/exp-*/**/*.jsonl.

Prometheus. Длительности — classic histogram (llm_ttfc_seconds, llm_request_duration_seconds, llm_queue_wait_seconds, llm_inter_chunk_seconds) с границами 25 мс … 60 с под шкалу имитатора. Перцентиль считается из суммарных bucket-счётчиков с сохранением le:

6. Ревью PR: «навсегда закрепить диалог за Pod»

Условия. У реплики A есть префикс диалога, но очередь ≈ 3 с. Реплика B свободна, пересчёт префикса ≈ 0,8 с. Решение: этот запрос отправить на B. Ожидаемое время до первой части на A ≈ 3 с очереди + стоимость hit (у нас 20 мс + новые сообщения) ≈ 3,05 с; на B ≈ 0 + 0,8 с. Закрепление «навсегда» выигрывает только при пустой очереди, а очередь на «своей» реплике растёт именно из‑за закрепления. Это видно в опыте B: при ClientIP-привязке и 80 % трафика от одного клиента горячая реплика копит очередь, вторая простаивает (раздел 2). PR в текущем виде не принимаю; принимаю мягкую привязку с ограничением загрузки.

Правило допуска нового запроса. Для каждой готовой реплики оценить TTFC_est = queue_wait_est + prefill(незакэшированные_токены) + hit_cost, выбрать минимум; при равенстве в пределах допуска (например, 20 %) — реплику с префиксом. Если на всех TTFC_est выше SLO или очередь полна — отказ 429 с Retry-After до постановки в очередь, а не тайм-аут после. Наш HAProxy-вариант — грубое приближение этого правила: хеш по сессии + hash-balance-factor (не больше 125 % средней загрузки). После переноса «домом» диалога становится B — префикс теперь там; иначе возникнет пинг-понг.

Каких измерений не хватает, чтобы решать не по одному числу. (1) Распределение, а не точка: p50/p95 ожидания в очереди A на горизонте 0,8 с — очередь может рассосаться; (2) prefill на B под текущей нагрузкой B (0,8 с измерено на пустой B? при batch‑интерференции дороже) и его влияние на decode уже идущих на B потоков; (3) доля и ценность попаданий: длина общего префикса, hit ratio по репликам, вытеснение из кеша на B после переноса; (4) вероятность продолжения диалога и интервал между ходами — окупится ли «прогрев» B; (5) память KV-кеша на B; (6) на настоящем движке — TTFT/TPOT по токенам, а не TTFC имитатора.

Потеря A. История диалога передаётся в запросе (у нас — в messages; в проде — во внешнем хранилище по session_id), кеш — только оптимизация. Следующий ход уходит на любую готовую реплику и платит полный prefill (0,8 с); корректность не страдает. Это проверено: tests/test_k8s_recovery.py удаляет Pod, обслуживший первый ход, и второй ход продолжается с контрольной строкой на другой реплике.

Уже начатый потоковый ответ. Не переносить посреди потока: он дописывается на той реплике, где начат. При штатном выпуске это обеспечивает grace period (preStop 5 с + SIGTERM → дренаж ≤ 45 с, у нас длинные потоки 25 с дописались, 0 оборванных — раздел 1.2). Если реплика упала посреди потока, клиент получает обрыв (у нас это отдельный исход truncated), повторяет запрос целиком с тем же request_id на другую реплику и отбрасывает частичный ответ; «склеивать» продолжение с середины нельзя без детерминированного декодирования и того же состояния.

Связь с кейсом. Character.AI в первичном источнике «Optimizing AI Inference at Character.AI» (research.character.ai/optimizing-inference, июнь 2024) описывает межходовой кеш KV и sticky sessions — запросы одного диалога маршрутизируются на тот же сервер, что даёт ~95 % попаданий в кеш. Это довод «за» привязку, но там привязка — средство удержать кеш, а не жёсткое правило: при недоступности сервера диалог пересчитывается, и ёмкость рассчитывается под долю промахов. Наши замеры показывают, где граница: пока очередь «своей» реплики меньше стоимости пересчёта, привязка выгодна; когда больше (3 с > 0,8 с) — нет. Поэтому: привязка как предпочтение, с ограничением загрузки и обязательным пересчётом при потере реплики.

7. Ограничения и источники

  • Все числа — модель нагрузки CPU-имитатора (backend_mode=simulated): стоимость prefill линейна по символам, decode — фиксированные 50 мс на часть, «кеш» — LRU хешей префиксов. Настоящая модель не подключалась, TTFT/TPOT/tokens/s не измерялись.
  • Один узел kind на ноутбуке: нет межузловой сети, переноса Pod между узлами и конкуренции за GPU.
  • Наблюдение Ready/EndpointSlice — опрос API раз в 1–3 с; события точны до интервала опроса.
  • Grafana-чарт grafana/grafana помечен как deprecated (перенесён в grafana-community); версия закреплена.
